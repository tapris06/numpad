## 1. 선택한 구성

| 항목 | 결정 |
| --- | --- |
| 게임 엔진 | Godot 4.7.2, .NET 에디션 |
| 게임·핵심 로직 언어 | C# |
| 렌더러 | Compatibility |
| 초기 배포 대상 | Windows x86_64 |
| 개발용 SDK | .NET 10 SDK, Windows x64 |
| 채보 작성 형식 | 넘패드 채보 `.npd`, 버튼 1~9 + 방향 R/C |
| 초기 배포 형태 | 실행 파일과 필요한 데이터·런타임 파일을 포함한 폴더를 ZIP으로 배포 |

확인일의 [Godot 공식 Windows 다운로드](https://godotengine.org/download/windows/)는 4.7.2와 해당 .NET 에디션을 제공한다. C# 개발에는 .NET 에디션과 SDK가 필요하다. [Godot C# 준비 사항](https://docs.godotengine.org/en/stable/tutorials/scripting/c_sharp/c_sharp_basics.html)

.NET SDK는 [Microsoft의 .NET 10 Windows x64 SDK](https://dotnet.microsoft.com/en-us/download/dotnet/10.0)를 사용한다. 프로젝트의 대상 프레임워크는 Godot 4.7.2가 생성하는 C# 프로젝트 설정을 기준으로 확인하고, 개발 환경 구성 시 실제 SDK 버전을 고정한다. SDK 버전과 프로젝트의 대상 프레임워크는 별개로 관리한다.

## 2. 선택 이유

이 프로젝트에 필요한 주요 기능은 2D 노트·판정선·3×3 블록 표시, 음악 재생, 키다운·키업 처리, 결과 UI다. 이 기능을 Godot에서 구성하고, 채보 해석과 판정 규칙은 C# 코드로 분리하는 구성을 선택한다. 이는 현재 사양을 기준으로 한 설계 판단이다.

Godot 공식 문서는 고급 렌더링이 필요하지 않은 2D 게임에 Compatibility를 선택할 수 있다고 안내한다. 현재의 도형·색상 기반 노트 표현에는 이 렌더러를 초기 기준으로 삼는다. [렌더러 선택](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html)

C#을 선택하는 이유는 채보 파서, 입력 판정, 롱노트 유지율, 배점 계산을 엔진 객체에 의존하지 않는 로직으로 작성하고 자동 검증하기 위해서다. 기존 사양의 조건과 경계값을 실제 입력·화면 코드와 구분하여 검증할 수 있다.

Godot는 음악 재생 시각과 출력 지연을 보정하는 API 및 리듬게임 동기화 안내를 제공한다. 이를 기반으로 곡의 시간과 판정을 맞추는 구조를 설계한다. [오디오 동기화](https://docs.godotengine.org/en/stable/tutorials/audio/sync_with_audio.html)

## 3. 엔진과 핵심 로직의 역할

| 구성 요소 | 책임 |
| --- | --- |
| 채보 파서 | 텍스트를 키·방향·목표 시각·종료 시각의 이벤트로 전개 |
| 채보 검증 | 동일 키 중복, 방향과 관계없는 키별 롱노트 닫힌구간의 다른 시작 탭 검출 |
| 판정 로직 | 입력 시각, 앞선 노트 우선 처리, 더 좋은 등급을 포함하는 판정 경계 |
| 롱노트 추적 | 시작점 판정에 따른 유지율 기준 시각, 키다운 누적, 유지분 판정 |
| 점수·콤보 | 정수 배점 분자 누적, 가중치 정규화, 소수점 버림, GOOD 이상 콤보 |
| Godot 입력 연결 | 넘패드의 키다운·키업을 핵심 로직에 전달 |
| 곡 시간 관리 | 음악 재생과 판정에 공통으로 사용할 곡 시각 제공 |
| 노트 표시 | R/C 레인, 현재 배치의 색상, 겹치는 노트 구간의 색 합성 |
| UI | 곡 선택, 플레이, 결과와 설정 화면 |

채보·판정·점수 로직은 Godot 노드와 분리된 C# 코드로 작성한다. Godot는 음악, 입력 연결, 표시와 UI를 담당한다. 구체적인 클래스·폴더 구성은 구현하면서 정한다.

채보 데이터에는 색이나 합성 그룹을 추가하지 않는다. 표시 단계에서 버튼과 방향으로 레인·원색을 구하고, 사양의 RYB 또는 RGB 합성표로 표시색을 결정한다. 원색별 판정 상태는 각각 유지한다.

## 4. 입력과 시간 처리 기준

### 넘패드 입력

Godot의 `InputEventKey`는 누름·해제·키 반복 이벤트를 구분하며, 별도의 넘패드 키 상수를 제공한다. `KEY_KP_1`~`KEY_KP_9`에 해당하는 입력을 연결하고, 자동 반복을 새 키다운으로 처리하지 않는다. [키 이벤트](https://docs.godotengine.org/en/stable/classes/class_inputeventkey.html), [넘패드 키 상수](https://docs.godotengine.org/en/stable/classes/class_@globalscope.html#enum-globalscope-key)

입력 이벤트 수신 시각을 기록하고, 눌림 상태가 바뀔 때 롱노트의 누적 시간을 갱신한다. Num Lock 상태에 따른 키 매핑과 실제 동시 입력 동작은 Windows에서 확인한다.

### 곡 시각과 판정 시각

- 판정은 곡의 목표 시각과 입력 시각을 비교하여 계산한다.
- 단조 증가하는 시간원을 사용하며, 내부 시간 저장은 64비트 정수 마이크로초를 기준으로 한다.
- 노트 위치는 현재 곡 시각과 목표 시각으로 계산한다.
- 음악 시작 시 오디오 믹스 대기 및 출력 지연을 반영한다.
- 일시정지·재시작 등 재생 상태가 바뀌면 곡 시각 기준도 함께 갱신한다.
- 채보의 `first`와 플레이 환경의 지연 보정은 각각 관리한다.

Godot의 `Time.get_ticks_usec()`는 단조 증가 시간원이다. 공식 동기화 안내의 시스템 시간 방식과 오디오 시각 방식을 참고하되, 초기 곡 재생은 출력 지연을 반영한 단조 시간 기준으로 구성하고 재생 위치와의 오차를 검증한다. [시간 API](https://docs.godotengine.org/en/stable/classes/class_time.html), [오디오 동기화](https://docs.godotengine.org/en/stable/tutorials/audio/sync_with_audio.html)

마이크로초 저장 단위만으로 실제 입력·출력의 정확도가 보장되지는 않는다. 키 이벤트 수신 지연과 오디오·표시 지연을 실제 플레이 환경에서 측정하고 보정한다. 기존의 ±30/60/90ms 판정 범위는 그대로 적용한다.

## 5. 초기 개발·배포 준비

1. Godot 4.7.2 .NET Windows x64 에디터를 준비한다.
2. .NET 10 SDK x64를 준비하고 에디터에서 C# 빌드가 가능한지 확인한다.
3. 동일 버전의 .NET 내보내기 템플릿을 준비한다.
4. Compatibility 렌더러로 C# 프로젝트를 생성한다.
5. 기존 예제 채보부터 파서·판정·점수 로직을 연결한다.
6. Windows x86_64로 내보내 음악 플레이와 결과 화면까지 확인한다.

Windows 배포는 Godot의 내보내기 기능을 사용한다. 내보낸 실행 파일과 PCK, C# 실행에 필요한 생성 파일을 함께 패키징한다. [Windows 내보내기](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_windows.html)

초기 구현 과정에서 Godot 4.7.2 .NET과 .NET SDK 10.0.403을 프로젝트의 `.tools`에 준비하고 C# 프로젝트를 생성했다. 에디터는 휴대형 설정을 사용한다. 이후 같은 개발 환경을 준비할 때는 루트의 `setup.ps1`을 실행한다.

## 6. 구현 시 검증할 항목

- 단타·롱노트·R/C 동시 입력의 파서 결과와 기존 이벤트 예제가 일치하는가.
- ±30/60/90ms와 유지율 50/75/100% 경계에 더 좋은 판정이 적용되는가.
- 시작점이 GOOD 이상일 때와 MISS일 때 롱노트 유지율의 기준 시각이 구분되는가.
- 색 합성을 표시 단계에서 처리하면서 각 키의 판정과 이펙트를 유지하는가.
- 오디오 지연을 보정한 뒤 한 곡 동안 노트·음악·판정의 시각이 맞는가.
- 실제 넘패드 키다운·키업과 동시 입력이 기대대로 동작하는가.
- 동일 키 롱노트의 닫힌구간 내 다른 시작 탭을 방향과 관계없이 거부하는가.
- 동시 성공·MISS가 섞이면 콤보를 끊은 뒤 성공 수로 새 콤보를 시작하는가.
- Windows 내보내기 결과에서 곡 끝까지 플레이하고 결과 화면으로 이동하는가.
