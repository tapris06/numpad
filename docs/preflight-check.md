## 2. 예제와 문서 검증

[텍스트 채보](../examples/charts/spec-demo.chart.txt)를 현재 예제의 BPM 120, 4분음표 간격으로 전개하여 [이벤트 JSON](../examples/charts/spec-demo.chart.json)과 비교했다.

- 입력 이벤트 9개: 단타 7개, 롱노트 2개.
- 두 롱노트의 구간: 1000~3000ms, 1500~2500ms.
- 마지막 입력 4000ms, 채보 종료 4500ms. 판정 완료 시간 확보.
- 방향·버튼·시작 시각·종료 시각이 JSON과 일치.
- 예제의 동일 키 동시 입력 및 방향과 관계없는 키별 롱노트 닫힌구간의 다른 시작 탭 충돌 없음.
- JSON에 색상·레인·합성 그룹 필드 없음.
- 총 배점 가중치 13, 전부 세부 퍼펙트일 때 1,010,000점으로 정규화.
- 구현 전 점검 당시 6개 문서의 로컬 링크 26개가 유효하며 UTF-8 읽기 이상 없음.

이 절은 구현 전 문서와 예제 데이터의 검증 기록이다. 이후 수행한 코드·플레이 검증은 구현 현황에 별도로 기록한다.

## 3. 최종 확정한 두 규칙

### 동시에 확정되는 성공·미스의 콤보

같은 시각에 확정되는 판정에 미스가 있으면 기존 콤보를 먼저 끊고, 굿 이상 판정 수만큼 새 콤보를 시작한다. 시간상 별도로 확정되는 판정은 발생 순서를 따른다.

예: 현재 콤보 120, 동시 성공 2개·미스 1개이면 처리 후 콤보는 2다.

### 키별 롱노트 닫힌구간의 다른 시작 탭 금지

키 k의 롱노트가 채보상 `[s, e]`이면, 다른 노트가 같은 키 k를 요구하는 시작 탭을 `s ≤ t ≤ e`에 배치할 수 없다. 방향과 관계없이 키별로 검사하고 양 끝점을 포함한다. 해당 롱노트 자신의 시작 탭은 제외한다.

새 단타와 새 롱노트의 시작 탭을 모두 검사한다. 동일 키 롱노트의 구간 중첩과 끝·시작이 맞닿는 배치도 금지다. 현재 기본 예제는 이 조건을 만족한다. 기존 롱노트를 놓았다가 다시 눌렀을 때의 유지 시간 누적은 기존 플레이 규칙을 따른다.

## 4. 실행 준비 상태

| 항목 | 현재 상태 | 준비할 내용 |
| --- | --- | --- |
| .NET SDK | `.tools/dotnet`에 10.0.403 준비 | 준비 완료 |
| Godot 실행 명령 | `.tools/godot`에 4.7.2 .NET 준비 | 준비 완료 |
| 내보내기 템플릿 | 4.7.2 .NET Windows x64 파일 준비 | 배포 스크립트에 연결 |
| 기본 데모 음원 | `content/audio/first-circuit.wav`, 36초 | EASY·NORMAL·HARD 채보 포함 |
| 두 번째 데모 음원 | `content/audio/long-wave.wav`, 44초·BPM 100 | 롱노트·롱잡 중심 EASY·NORMAL·HARD 포함 |
| 세 번째 데모 음원 | `content/audio/spark-rush.wav`, 44초·BPM 200 | 동타가 적은 단타 중심 EASY·NORMAL 포함 |
| 게임 프로젝트 | 초기 플레이 버전 구현 | 사용자 직접 테스트·개선 |

개발 도구는 프로젝트 안에 준비했다. 기존 사양 예제의 `music.wav`는 교체용 경로이며, 실제 게임은 기본 데모 음원을 사용한다.

## 5. 구현하면서 조정할 사항

화면 크기·노트 간격·색상값·스크롤 속도·지연 보정, 곡 선택과 결과 화면의 구성은 플레이 검증을 하면서 정리한다. 게이지와 실패 조건은 첫 플레이 완료 범위를 구현하면서 구체화한다. 미러·색 배치·RGB 반전·판정선 위치 조절·채보 편집기는 기존대로 후순위다.

착수 순서는 환경 구성 → 채보 파서·검증 → 판정·롱노트·점수 → 음악·입력·노트 표시 연결 → 한 곡과 결과 화면 → Windows 내보내기 검증이다.
